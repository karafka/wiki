# Upgrading to Web UI 1.1

!!! tip "Karafka 2.6 And karafka-core 2.6.3 Are Required"

    Karafka Web UI `1.1` requires Karafka `2.6` and `karafka-core` `>= 2.6.3`. The `karafka-core` floor is higher than the one `1.0` required, so a lock file pinning an older `karafka-core` needs to be updated as part of this upgrade.

Before upgrading to Karafka Web UI `1.1`, review our [General Karafka Upgrade Guide](Upgrades-Upgrading) first. This document provides essential advice on upgrading Karafka and its components and general best practices to ensure a smooth transition. The general guide contains fundamental steps that apply to all upgrades, while this specific guide focuses only on the changes introduced in the Web UI `1.1` release.

This release ships no changes to the consumer reporting schema and removes no configuration settings. For most users it is a drop-in upgrade. There is one change that requires action before you deploy, and it affects only Pro users who run a custom messages policy.

## Custom Messages Policies Must Add A Publish Method

The Explorer gains a **Publish message** capability in Pro: you can produce an arbitrary message to a topic or a chosen partition, with an optional key, validated headers, and a typed, uploaded or tombstone payload. It is a separate action from republishing an existing message.

The capability is gated by a new `publish?` policy method, and it is **enabled by default**.

This matters if you use the Web UI [policies engine](Pro-Web-UI-Policies) to control what your users can do. A messages policy previously needed six methods (`key?`, `headers?`, `payload?`, `download?`, `export?` and `republish?`). It now needs a seventh, `publish?`.

!!! warning "A Custom Policy Without This Method Raises An Error"

    The Explorer calls `publish?` on your configured messages policy directly, without checking whether the method exists. A custom policy class written against Web UI `1.0` does not define it, so opening an Explorer topic view raises a `NoMethodError` until you add the method. Add it before you deploy.

Unlike the other messages policy methods, `publish?` receives a topic name as a `String` rather than a `::Karafka::Messages::Message`, because the message it guards does not exist yet:

```ruby
class MyCustomMessagesPolicy
  # ... your existing six methods ...

  # @param _topic [String] name of the topic to which we want to publish a message
  # @return [Boolean] true if we should allow publishing
  def publish?(_topic)
    true
  end
end
```

To keep the behavior you had before this release, where producing new messages from the Web UI was not possible at all, return `false`:

```ruby
def publish?(_topic)
  false
end
```

Because the policy receives the topic name, you can also allow it selectively:

```ruby
def publish?(topic)
  # Allow producing test messages, but never to the production order stream
  topic.start_with?('sandbox_')
end
```

Returning `false` hides the **Publish message** action in the Explorer and rejects a crafted request to the publishing endpoint, so the control holds even if a user knows the URL.

If you do **not** configure a custom messages policy, there is nothing to do. The default policy allows publishing, and the capability appears in the Explorer after the upgrade.

## Aggregated Health Views

The Pro Health views are aggregated per topic instead of per partition, so they stay readable on clusters with many partitions. Each topic is one summary row (lag, maximum and average lag, a skew flag, LSO risk and paused partitions) that drills down into the per-partition views you had before. No data is lost, and the per-partition detail is one click away.

The thresholds that drive the flags and row highlighting are configurable under `config.ui.health.lags`:

The defaults mean a lag of `5_000` or more is a warning and `10_000` or more is an error:

```ruby
Karafka::Web.setup do |config|
  config.ui.health.lags.high_threshold = 50_000
  config.ui.health.lags.skew_threshold = 5
end
```

A `skew_threshold` of `1` or less is now rejected. The value is a multiplier of the average lag, so anything at or below `1` flagged every multi-partition topic as skewed.

## Commands Are Confirmed By The Broker

Consumer commanding requests (pause, resume, seek, quiet, stop and trace) and scheduled-message cancellations are produced through an acknowledged producer (`acks: 1`) instead of the fire-and-forget one. A command that the broker does not accept now surfaces as an error rather than being dropped silently.

This needs no configuration. A new `Karafka::Web.producers` facade exposes the variants if you want to reach them directly, and `Karafka::Web.producer.acked` returns an `acks: 1` producer (idempotent and transactional producers are returned unchanged).

## Per-Broker Partition Distribution

The Cluster section gains a **Distribution** view in Pro: a leader-partitions chart plus each broker's leader, follower and replica counts, shares and out-of-sync replicas, with over and under-loaded brokers flagged. It is a new read-only view and requires no configuration.

## Deployment

This release does not change the consumer reporting schema, so the zero-downtime dance that schema bumps require does not apply here:

1. Add the `publish?` method to your custom messages policy if you have one, as described above.
1. Test the upgrade on a staging or dev environment.
1. Perform a rolling deployment (or a regular one) and replace all consumer processes.
1. Update the Web UI Puma.
1. **No** CLI command execution is required.
1. **No** migration is required.
1. Enjoy.
